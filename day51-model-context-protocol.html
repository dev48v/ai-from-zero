AIFromZero · Day 51

🔌 Model Context Protocol — one open standard that lets any AI app plug into any tool or data source, the way USB-C lets any laptop plug into any device. Before MCP, every AI app had to hand-write a bespoke integration for every tool it wanted to reach — M apps × N tools = M×N connectors, none reusable. MCP (an open standard from Anthropic, 2024) collapses that to M+N: an MCP host (the AI app — Claude Desktop, an IDE, an agent) runs one MCP client per connection, and each client speaks a uniform JSON-RPC protocol to an MCP server that exposes its capabilities. Write a server once and every MCP host can use it; write a client once and it can talk to every server. A server exposes three kinds of thing — tools (actions the model can invoke), resources (read-only data addressed by URI), and prompts (reusable templates). This is not a replacement for plain function-calling (Day 28) — MCP is the interoperable transport and discovery standard built around it, so the same tool works across apps without rewriting glue. Below, pick a server, watch its client handshake and tools/list to discover what it offers, then watch a live request flow: the model decides to call a tool → the client sends a tools/call over the wire → the server runs real code → the result comes back → the model answers. Every JSON-RPC message is shown as it flies.

The exchange, step by step — the lit beat is where we are now

A full request-response cycle: a one-time lifecycle handshake (initialize), a discovery round (tools/list), then the use loop that repeats every time the model needs the tool. Notice discovery happens once — after that the host knows what the server can do and just issues tools/call whenever the model decides to.

MCP is an open standard that puts a uniform, JSON-RPC client-server protocol between AI apps and the tools/data they use — so any host can use any server without bespoke glue, turning an M×N integration mess into M+N. A server exposes tools (model-invoked actions), resources (URI-addressed read-only data), and prompts (reusable templates); the client discovers them with */list and invokes them with */call or */read. It's built on function-calling (Day 28), not instead of it: the model still emits a structured call, but MCP standardises how that call is discovered, transported (over stdio locally or HTTP remotely), and answered — which is why one server works in Claude Desktop, an IDE, and a custom agent alike.

🔨 Build an MCP exchange from the wire up

    
Reproduce the whole LOOK engine as real MCP messages: a server that declares tools, resources, and prompts; a client that handshakes with initialize, discovers capabilities with tools/list, and invokes them with tools/call; and the model loop that turns a user question into a tool call and a result into an answer. Every block below is a genuine JSON-RPC 2.0 envelope — the exact shapes flowing across the wire in LOOK — followed by how you'd wire it with a real SDK.

    
    
      
  1. 
        
    1
    Everything is JSON-RPC 2.0
    
        
    MCP is just JSON-RPC 2.0 between a client and a server. A request carries an id, a method, and params; the matching response echoes the id and carries a result (or an error). One-way notifications have a method but no id. That's the entire envelope — tools, resources, and prompts are all just methods.
    
        
    // request  (client → server) — has an id, expects a reply
{ "jsonrpc": "2.0", "id": 1, "method": "tools/list", "params": {} }

// response (server → client) — echoes the id
{ "jsonrpc": "2.0", "id": 1, "result": { "tools": [ /* … */ ] } }

// notification (either direction) — no id, no reply
{ "jsonrpc": "2.0", "method": "notifications/initialized" }

    The lifecycle — initialize handshake
    
        
    Every connection opens with initialize: the client announces its protocol version and capabilities, the server replies with its capabilities and serverInfo. This is capability negotiation — both sides learn what the other supports before any real work. The client then sends the notifications/initialized notification and the session is live.
    
        
    // → client announces itself
{ "jsonrpc":"2.0", "id":0, "method":"initialize", "params":{
    "protocolVersion":"2025-06-18",
    "capabilities":{ "roots":{}, "sampling":{} },
    "clientInfo":{ "name":"claude-desktop", "version":"1.0" } } }

// ← server replies with what IT can do
{ "jsonrpc":"2.0", "id":0, "result":{
    "protocolVersion":"2025-06-18",
    "capabilities":{ "tools":{}, "resources":{}, "prompts":{} },
    "serverInfo":{ "name":"filesystem", "version":"0.6" } } }

  3. 
        
    3
    Discovery — tools/list advertises the catalog
    
        
    Now the client asks what the server offers. Each tool comes back with a name, a description (the model reads this to decide when to use it), and an inputSchema (JSON-Schema for its arguments). resources/list and prompts/list work identically. The host injects these tool definitions into the model's context — this is the bridge to function-calling (Day 28).
    
        
    // → what can you do?
{ "jsonrpc":"2.0", "id":1, "method":"tools/list", "params":{} }

// ← the advertised tools (schema drives the model's call)
{ "jsonrpc":"2.0", "id":1, "result":{ "tools":[
  { "name":"read_file",
    "description":"Return the contents of a file",
    "inputSchema":{ "type":"object",
      "properties":{ "path":{ "type":"string" } },
      "required":["path"] } },
  { "name":"list_directory", "description":"List a folder", /* … */ }
]}}
    
      
    4. 
      
  4. 
        
    4
    The model decides & the client sends tools/call
    
        
    The user asks a question. The model — seeing the advertised tools — emits a structured call: a tool name and its arguments (exactly like function-calling). The host's client packages that decision as a tools/call request and sends it to the server over the transport. The model doesn't run anything itself; it only asks.
    
        
    // model's decision, packaged by the client and sent to the server
{ "jsonrpc":"2.0", "id":2, "method":"tools/call", "params":{
    "name":"read_file",
    "arguments":{ "path":"/project/README.md" } } }
// name + arguments come straight from the model's tool call.
    
      
    5. 
      
  5. 
        
    5
    The server runs real code & returns a result
    
        
    The server executes the tool — actually reading the file, hitting the GitHub API, or running the SQL — and returns a result whose content is a list of blocks (text, image, etc.), plus an isError flag. The result flows back over the wire to the client, which hands it to the model as the tool's output.
    
        
    // ← the server's answer for id:2
{ "jsonrpc":"2.0", "id":2, "result":{
    "content":[ { "type":"text",
                  "text":"# AIFromZero\nOne big AI idea a day…" } ],
    "isError": false } }
// on failure: isError:true and content describes what went wrong.

  6. 
        
    6
    Resources & prompts — the other two primitives
    
        
    Resources are read-only data addressed by URI (a file, a DB row, a wiki page) — the app chooses which to pull into context. Prompts are reusable, parameterised templates the user invokes (like slash-commands). Same list/fetch shape as tools, different control: tools are model-controlled, resources app-controlled, prompts user-controlled.
    
        
    // resources: addressed by URI, read (not called)
{ "jsonrpc":"2.0", "id":3, "method":"resources/read",
  "params":{ "uri":"file:///project/README.md" } }

// prompts: a named template with arguments
{ "jsonrpc":"2.0", "id":4, "method":"prompts/get",
  "params":{ "name":"summarize_file",
             "arguments":{ "path":"/project/README.md" } } }

  7. 
        
    7
    Transports — stdio vs HTTP
    
        
    The messages are the same; only the pipe differs. stdio: the host launches the server as a local subprocess and talks over stdin/stdout — perfect for local tools (a filesystem, a git repo). Streamable HTTP: the server is a remote web endpoint — for hosted/shared servers. A host wires up servers in a small config; each entry becomes one client.
    
        
    // a host config: each server → one client connection
{ "mcpServers": {
    "filesystem": {                      // local, over stdio
      "command": "npx",
      "args": ["-y","@modelcontextprotocol/server-filesystem","/project"] },
    "github": {                          // remote, over HTTP
      "type": "http",
      "url": "https://api.example.com/mcp" }
} }

    8
    In practice — an SDK server & a host
    
        
    You don't hand-write JSON-RPC — an SDK (Python mcp, TypeScript @modelcontextprotocol/sdk) turns a decorated function into a fully-advertised tool, handling initialize, tools/list, and tools/call for you. On the host side, apps like Claude Desktop and IDEs are MCP clients out of the box — point them at your server and the model can use it. Write the server once; every MCP host benefits.
    
        
    # server side — Python MCP SDK (FastMCP)
from mcp.server.fastmcp import FastMCP
mcp = FastMCP("filesystem")

@mcp.tool()                                   # auto-advertised via tools/list
def read_file(path: str) -> str:
    """Return the contents of a file."""      # ← becomes the description
    return open(path).read()                  # ← runs on tools/call

@mcp.resource("file://{path}")                # a URI-addressed resource
def file_resource(path: str) -> str:
    return open(path).read()

mcp.run()            # speaks MCP over stdio; any host can now connect
# host side: add it to the app's mcpServers config — that's the whole wiring.
