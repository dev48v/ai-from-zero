AIFromZero · Day 43

🐍 State-Space Models / Mamba — the transformer alternative. An attention model re-reads the whole history for every new token, so its cost grows with the square of the length and its memory grows with the length — a wall you hit on very long inputs. An SSM instead keeps a fixed-size state and updates it token-by-token (like a smart running summary): constant memory, linear time, and it can stream forever. Mamba's twist is selectivity — the state update depends on the input, so the model can choose what to remember and what to forget. The tradeoff: pinpoint recall (attention's strength) vs raw efficiency (the SSM's).

Feed a stream, token by token — watch attention's cost explode while an SSM stays flat

Two ways to process a sequence, side by side. Attention lets every new token look back at all the tokens before it — brilliant for recall, but every step re-reads the whole history, so the running cost climbs like n² and the memory (the KV cache) grows with the length. A state-space model instead folds each token into one fixed-size state and moves on — the per-token work never changes, so total cost is linear and memory is constant, no matter how long the stream. Below, both counters are computed live as you advance the stream. Card ② runs the actual SSM recurrence h = a·h + b·x in your browser, with a selective gate you can flip on and off. No neural net, no server.

② The recurrent state — h = a·h + b·x — with a selective gate — run the real recurrence on a token stream

This is the actual SSM math, running live. Each token updates a single running state h: keep a fraction a of the old state, add b times the new input. Flip selectivity on and the tokens change a and b based on their content: ⟂ reset forces a≈0 (new topic — flush the past), ★ keep forces a≈0, b≈1 (important — write this value in), and · noise forces a≈1, b≈0 (irrelevant — hold what I have, ignore it). A non-selective SSM uses the same a,b for every token, so it can't make any of those choices — that's exactly the weakness Mamba fixes.

🔎 Same recurrence, two behaviours. Watch what happens at ⟂ and ★: the selective line snaps — it flushes on reset and freezes on keep. The non-selective line just leaks at one fixed rate, unable to tell an important token from noise. That input-dependent gating is the whole idea behind Mamba, and it's what let a fixed-size state finally rival attention.

Attention buys perfect recall by re-reading everything — at a cost that grows like the square of the sequence length and a memory that grows with it. A state-space model trades that for a fixed-size running state: linear time, constant memory, and the ability to stream indefinitely. Plain recurrence was too forgetful to compete — until Mamba's selectivity made the state update depend on the input, so the model can choose what to remember and what to forget. That's why SSMs matter for very long context, streaming, and on-device / edge — and why the frontier increasingly reaches for hybrids that keep a little attention for recall alongside cheap SSM layers.

🔨 Build a selective state-space model from scratch

    
Reproduce the whole LOOK demo: the two cost models that show the quadratic wall, the real scalar recurrence h = a·h + b·x, a full run over a token stream, and the selective gate that lets the state choose what to remember. This is the exact engine powering LOOK ① and ②.

    The two cost models — the quadratic wall vs linear streaming
    
        
    Attention lets token t look back at all t tokens before it, so per-token work is t and the total after n tokens is n(n+1)/2 ≈ n²/2 — and it must cache all n keys/values. An SSM only ever touches its fixed state of size d, so per-token work is a constant d, the total is d·n (linear), and memory is just d — forever.
    
        
    // ATTENTION: re-reads the whole history every token
const attnPerToken = t => t;                 // t = position (1..n)
const attnTotal    = n => n * (n + 1) / 2;   // ~ n^2 / 2  -> the wall
const attnMemory   = n => n;                  // KV cache grows with length

// SSM / MAMBA: one fixed-size state, updated in place
const ssmPerToken  = d => d;                  // CONSTANT (state size)
const ssmTotal     = (n, d) => d * n;         // LINEAR in length
const ssmMemory    = d => d;                  // CONSTANT — streams forever

attnTotal(1024);        // 524,800  (quadratic)
ssmTotal(1024, 16);     //  16,384  (linear)  -> ~32x less work

    The scalar recurrence — a running, decaying summary
    
        
    The heart of an SSM is one line. Keep a fraction a of the old state (a near 1 = long memory, near 0 = forget fast), add b times the new input x, and read the output out with c. No history is stored — everything the model "knows" is compressed into h.
    
        
    // state update: h_t = a * h_{t-1} + b * x_t
function ssmStep(h, x, a, b){ return a * h + b * x; }
// readout:       y_t = c * h_t
function readout(h, c){ return c * h; }

// 'a' in [0,1] = how much of the PAST survives (the "forget" dial)
// 'b'          = how strongly the new input enters the state
// 'c'          = how the state is projected back out

    Run a stream through it — one pass, constant memory
    
        
    Streaming is just a loop: for each token, update the single state and emit an output. Notice there's no growing array of past tokens — only h lives between steps. That's the whole reason an SSM can process a million-token stream in constant memory.
    
        
    function runFixedSSM(xs, a, b, c){
  let h = 0; const ys = [];
  for (const x of xs){          // one token at a time
    h = ssmStep(h, x, a, b);    // update the fixed state
    ys.push(readout(h, c));     // emit output
  }
  return ys;                     // memory used: ONE number, always
}
runFixedSSM([2,4,7,6,0,0,0], 0.7, 0.5, 1);

    The weakness of a fixed SSM — it can't tell signal from noise
    
        
    With the same a,b for every token, the state leaks at one fixed rate. It has no way to say "this token matters, hold it" or "new topic, dump the old stuff". A burst of noise decays at the same speed as a crucial fact. This input-blindness is why classic linear SSMs and RNNs lagged behind attention on recall-heavy tasks.
    
        
    // fixed (LTI) SSM: a and b never change, whatever the token is
const a = 0.7, b = 0.5;
// a "reset" token (x=0) does NOT flush — the past still survives:
//   h = 0.7 * h_old + 0.5 * 0  =  0.7 * h_old
// a "keep" token can't be locked in — it decays like everything else.
// => the model cannot CHOOSE what to remember.

    Selectivity — Mamba's twist: make a, b depend on the input
    
        
    Mamba makes the parameters functions of the current token. Now the model can gate its own memory: on a "new topic" token drive a→0 to flush the state; on an "important" token drive a→0, b→1 to write the value in cleanly; on an "irrelevant" token drive a→1, b→0 to hold what it has and ignore the input. That content-aware remember/forget is exactly what a fixed SSM lacked — and it's computed live in LOOK ②.
    
        
    // selective: a and b are chosen from the TOKEN's content
function selectiveA(tok, baseA){
  if (tok.type === "reset") return 0.04;  // "forget the past"  -> flush
  if (tok.type === "keep")  return 0.05;  // "write this value" -> clear old
  if (tok.type === "noise") return 0.98;  // "ignore this"      -> hold state
  return baseA;                           // otherwise: normal decay
}
function selectiveB(tok, baseB){
  if (tok.type === "keep")  return 1.0;   // let the important value in fully
  if (tok.type === "noise") return 0.0;   // block the irrelevant input
  return baseB;
}

    Put it together — the selective streaming loop (+ why it's still fast)
    
        
    Swap the fixed a,b for the token-dependent ones and you have a selective SSM: it flushes on reset, freezes on keep, and still runs in one pass with constant memory. The catch: input-dependent parameters break the simple convolution trick — so Mamba uses a hardware-aware parallel scan to train fast on GPUs, then runs as a plain recurrence at inference.
    
        
    function runSelectiveSSM(tokens, baseA, baseB, c){
  let h = 0; const ys = [];
  for (const tok of tokens){
    const a = selectiveA(tok, baseA);   // chosen per token
    const b = selectiveB(tok, baseB);
    h = ssmStep(h, tok.x, a, b);        // same one-line update
    ys.push(readout(h, c));
  }
  return ys;
}
// training: an associative PARALLEL SCAN computes all h_t at once on GPU;
// inference: the plain O(1)-memory recurrence above, streaming forever.
