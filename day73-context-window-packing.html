🧩 Context-window packing — every packer reports it filled the window, and that number cannot tell you whether the answer is still in there.

Six packers, one budget, one corpus. Utilisation — the fraction of the window you actually filled, the number every retrieval stack prints — separates them by almost nothing. Whether the sentence that answers the question survived separates them by a factor of several. The control fills the window best of all and keeps the answer least.

The scoreboard

The control

truncate is greedy_score plus one line: when the next document does not fit, put in as much of it as fits. It is the packer almost every hand-rolled context builder actually is.

Exact optimisation is not the fix

knapsack maximises total relevance exactly, by dynamic programming over the budget. It is optimal for the thing it optimises.

Counting tokens by dividing by four

The corpus carries a true token count per document. The estimator every quick script uses is chars/4.

What is actually being measured

A packing problem here is a budget B and a set of documents, each with an integer token cost, an integer relevance score, and a flag saying whether it carries the span that answers the question. Exactly one document per corpus carries it.

  • utilisation = tokens placed / B. Never above 1.
  • score = sum of the relevance of whole documents placed.
  • answer kept = the answer document was placed whole. A truncated answer document does not count, because the span it carries is what the truncation removed.

The six packers differ only in which documents they choose:

  • greedy_score — highest relevance first, skip anything that does not fit.
  • greedy_density — highest relevance per token first.
  • knapsack — exact 0/1 dynamic programme; maximum achievable score.
  • recency — newest first, which is what a chat history does.
  • answer_oracle — places the answer document first, then greedy density. Not a real policy; it is the ceiling.
  • truncate — the control.
Why the ceiling is in the table. Without answer_oracle you cannot tell whether a low answer-kept rate is the packer’s fault or the budget’s. It separates “this packer threw the answer away” from “the answer never fit”.

Why utilisation cannot see the difference

Utilisation is a property of the total. Any packer that keeps taking documents until nothing else fits ends up in the same narrow band, because the band is set by the size of the documents, not by which ones you chose. Two packers that disagree about every single document can report utilisation to within a percentage point of each other.

The answer-kept rate is a property of one specific document. Nothing about filling the window constrains it, which is exactly why the number that is easy to print is the number that carries no information about the thing you care about.
