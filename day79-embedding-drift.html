AIFROMZERO · DAY 79

🧩 Embedding drift — the provider ships v2, or someone changes the tokenizer, and the index is still there, still returning five results, still with plausible scores. Nothing here calls an embedding API and nothing is a black box: the embedder is a hashed bag-of-tokens implemented in full — FNV-1a with a stated seed, the signed hashing trick, optional idf, L2 normalisation, cosine — so a “version” is a concrete configuration and a version change is one people actually make. The corpus is synthetic and declared, 12 topics × 10 documents, so every retrieval can be scored for correctness rather than only for agreement with an earlier run. Healthy precision@5 is 0.9417; chance is 0.0833. 🔴 The version changes your vector store can catch are the ones that barely matter, and the ones it cannot catch are the ones that destroy retrieval. Change the width and the vector is the wrong shape, so a typed index rejects it outright — and even if it did not, precision only falls to 0.7750. Change the hash seed or the tokenizer and the width is identical, nothing rejects anything, and precision falls to 0.0917, 0.1000 and 0.0333 — at or below chance. 🔴 Re-embed only the new documents and they become nearly invisible: the 60 freshly embedded ones take 21.67% of the top-5 slots where a single-version index gives them 52.50%. 🔴 And the alarm you would rely on is the wrong shape too — on that half-migrated index the mean top-1 cosine falls 29.8% while precision falls 50.4%, so a score threshold set to catch the total failure sails straight past the partial one, which is the one that actually happens.

The vectors carry no version tag. An index is an array of numbers; a query is an array of numbers; cosine is happy to compare any two of the same length. There is no place in that path where a mismatch can be detected, and that is the whole subject of this page — not that re-embedding is hard, but that not re-embedding is silent.

One query, two embedders

The index is always the same one, built once with the base version. Only the embedder that turns the question into a vector changes. Where a row is marked wrong, the retrieval returned a document about a different topic entirely — with a score, and with no error.

what a threshold would see

1. The detectable failures are the mild ones

🔴 Sort this table by damage and you get almost exactly the reverse of sorting it by detectability. A width change produces a vector of the wrong length, which any typed vector store refuses before the query runs — and it is the least harmful of the changes here. A seed or tokenizer change produces a vector of exactly the right length, full of plausible floats, which nothing anywhere will object to — and it takes retrieval to chance. The 3-gram row lands at 0.0333, which is below the 0.0833 you would get by returning five documents at random.

2. Re-embedding only the new documents

🔴 This is the version of the mistake that actually gets made: the migration script runs on new ingests and nobody backfills. Half the index is in one space, half in another, and the query can only be in one of them. The documents that do not match the query’s version are not wrong, they are unreachable — they take 21.67% of the slots where an even-handed index gives them 52.50%. The failure has no error message and no empty result set: the system returns five documents every time, drawn from the half that happens to still line up.

3. The score is a weak alarm, and weakest where it matters

The obvious monitor is the similarity score, and on a total mismatch it does move: mean top-1 cosine falls from 0.5689 to about 0.23. So a threshold would catch the case where somebody swapped the embedder wholesale. 🔴 On the half-migrated index it falls only to 0.3992 — a 29.8% dip — while precision falls 50.4%. Every query still has a well-matched document somewhere in the half that lines up, so the top score stays respectable while half the corpus has quietly left the building. A threshold tuned on the loud failure will not fire on the quiet one.

4. Even the correct migration moves your answers

Re-embedding everything is the right fix and it works: precision comes back to 0.858–0.958, in one case slightly above the original. But the top-5 overlap with the old index runs from 0.933 down to 0.725, so between 6.7% and 27.5% of the retrieved documents are different afterwards — least for the idf change, most for switching tokenizer. Nothing is broken. It is simply that any prompt, cache, evaluation set or human sign-off that was pinned to the old results is now pinned to results that no longer come back — and unlike the failures above, this one happens on the day you do everything right.

What this covers, and what it does not

The embedder is a hashed bag-of-tokens, not a neural model. That matters for how you read the rows: a hash-seed change produces two unrelated spaces, which is the extreme case and an upper bound, not a prediction for what v1→v2 of a trained model does — two versions of a real model usually stay far closer than that. The tokenizer rows are the better analogue, and they are nearly as bad. Nothing here models semantic drift: there is no meaning in this corpus beyond term overlap, so this page says nothing about a v2 that is simply better at understanding a question. The corpus is synthetic, 120 documents with one topic each, 24 queries, top-5, plain cosine, no chunking, no reranker, no hybrid keyword leg — each of which would change the numbers. The claim is narrow and it is about plumbing: a vector index cannot tell you which embedder produced it, and every consequence above follows from that.

How it works

// the signed hashing trick - a real embedder, ~15 lines
const h    = fnv1a(token, cfg.seed);
const slot = h % cfg.dim;
const sign = (h >>> 31) & 1 ? -1 : 1;
v[slot] += sign * weight;

// and the line that has nowhere to fail
const qv = embed(query.text, queryCfg, queryIdf);   // queryCfg need not match
scored = index.vecs.map((v, i) => ({ i, score: cosine(qv, v) }));

Self-check

Runs on load. The controls carry the argument: “a mismatch destroys retrieval” means nothing unless the matched case is checked to work, unless the same-version row is checked to be bit-identical, and unless the chance baseline is computed rather than asserted.
