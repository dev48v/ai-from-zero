⚖️ Multi-tenant fairness — turning on the fairness feature made it 5.8× less fair. Four tenants on one replica: same prompts, same offered load measured in GPU-seconds, all four permanently backlogged, the same 120 seconds of the same GPU, the same bill. First-come-first-served splits the machine 25.9 / 26.8 / 24.7 / 22.6. Switch on equal per-tenant request quotas and it splits 7.4 / 11.3 / 30.3 / 51.0 — 6.87× against 1.18×, decided by one number that is in nobody's config and cannot be known at admission: how many tokens the model is about to generate. Then the published fair scheduler equalises its own counter to 1.014 and hands out the machine 3.05× unequally; a per-tenant slot cap splits decode time 24.7 / 25.2 / 25.2 / 24.9 and still misses by 1.92×; and the repair is one word — count milliseconds. Pure vanilla JavaScript, one file, no build step.

what the scheduler does

One replica, continuous batching, four tenants, five worlds of 120 simulated seconds each, one number per configuration averaged over all of them. Nothing here simulates language: a request has a prompt length and an output length, an iteration decodes one token for every resident sequence and takes 9 + 0.55·B ms, a prefill costs 0.06 ms per prompt token and stalls the batch, and when the KV cache fills the engine preempts by recompute. Every policy is given exactly the same machine for exactly the same 120 seconds, so the bill is identical by construction and the only thing that changes is who gets it. The share of the machine a tenant received is measured in GPU-milliseconds and the four shares sum to 1.000000, because an iteration of batch B is charged dt / B to each resident sequence.

SELF-TEST

running…

Every fairness knob you can buy is denominated in requests. The GPU is spent in milliseconds.

Put four teams on one inference replica. They all pay the same. They all send the same prompts. Arrange it so they all offer the same amount of work measured in the resource itself — each one asks for three times its quarter of the machine, so all four queues stay backlogged for the whole window and “fair share” is a well-defined thing. The only difference between them is what they do: the first classifies, and its answers are about 24 tokens. The fourth runs an agent loop, and its answers are about 354.

Do nothing. Plain first-come-first-served.

The machine splits 25.9 / 26.8 / 24.7 / 22.6. Biggest over smallest: 1.18×. Nobody is being starved. A single global FIFO queue, no counters, no quotas, no config.

Now switch on the fairness feature: an equal requests-per-minute quota for every tenant.

The machine splits 7.4 / 11.3 / 30.3 / 51.0. Biggest over smallest: 6.87×. The classify team is down from 25.9% of the replica to 7.4%; the agent team is up from 22.6% to 51.0%. Nothing else changed — same tenants, same prompts, same offered load, same replica, same 120 seconds, same bill. Every tenant is comfortably inside its quota. Every dashboard is green. Turning on fair queuing made the split 5.8× less fair.

The parameter is the realised output length, and it is in nobody's config

A quota admits requests. A round-robin dispatches requests. A rate limit counts requests. All three control the same variable: how many times a tenant gets to start. What a tenant actually consumes is residency — how long its sequences sit in the running batch taking one slot of every decode iteration — and residency is the output length. So the exchange rate between “one request” and “one millisecond of GPU” is a number that:

  • is not in the operator's config, because the operator never chose it;
  • is not in the client's config either — max_tokens is a ceiling, not a length;
  • is not knowable at admission time, because it is decided by the model, one token at a time, after the request has already been let in;
  • and is the only thing separating a 1.18× split from a 6.87× one.

Slide the output-length spread from 0 to 1 on the MEASURE tab and watch it happen. At spread 0 every tenant's answers are the same length and every scheduler on the page lands between 1.01× and 1.13× — a quota is exactly fair, round-robin is exactly fair, doing nothing is exactly fair. Nothing about the schedulers changed on the way to spread 1. Only the thing none of them can see.

Why FIFO wins here, and exactly when it stops

FIFO is not fair. FIFO hands out service in proportion to offered load: when every queue is deep, the oldest head belongs to whichever tenant has been admitted least relative to what it sent, so admissions settle proportional to arrival rate and service settles proportional to demand. That is why it scores 1.18× in a world built so that demands are equal — it is fair here by coincidence, and the coincidence is the experiment's design, not a property of FIFO.

Push the flood slider and the coincidence dies. Let the agent tenant offer 4× what the others offer and FIFO gives it 53.5% of the replica; at 8× it gives it 68.3%, and the predicted share offeri / Σ offerj tracks it to within a point and a half at every setting. FIFO has no isolation at all: the way to get more of a shared replica under FIFO is to ask for more of it.

Reproducing the published result, and then watching it inverT

Virtual Token Counter (Sheng et al., Fairness in Serving Large Language Models, OSDI 2024) is the right answer to that. Give each tenant a counter, add wp per prompt token and wo per generated token as the service is delivered, always dispatch to the lowest counter, and lift a returning tenant's counter to the running minimum so an idle client cannot bank a deficit and cash it in. The page reproduces the paper's direction cleanly: against an equal requests-per-minute quota at 6.87×, VTC scores 3.05×, less than half the gap, and unlike FIFO it does not care at all what anyone floods — it holds 3.0× from flood 1 to flood 8 while FIFO decays from 1.18× to 7.17×.

And then the ranking inverts. In the default world — equal offered load, everyone backlogged — the published fair scheduler is 2.6× worse than having no scheduler at all. FIFO 1.18, VTC 3.05. Walk the flood slider and the crossover sits between 3× and 4×: below it, deleting your fair queuing improves fairness; above it, VTC is the only thing standing between you and one tenant owning the box. Both halves are true. Neither is the headline on its own.

The algorithm is correct. The denominator is wrong.

VTC does precisely what it promises. Measure its own counter — weighted tokens, wp=1, wo=2 — and the four tenants come out at 24.9 / 24.9 / 24.9 / 25.2, a ratio of 1.014. It equalises its counter to within a percent and a half. Measure the machine and the same run reads 12.8 / 17.2 / 31.1 / 38.9, a ratio of 3.05. There is no bug. Weighted tokens and GPU milliseconds are simply not the same quantity, and the algorithm was only ever asked to equalise the first one.

What the two weights are actually worth

On this replica a prefill token costs 0.06 ms and a decode token costs (9 + 0.55·B) / B ms of machine per resident sequence — 0.925 ms at a batch of 24. So the machine's own exchange rate is wo / wp = 15.42. The weights that ship are 1 and 2. Set wo to 15.42 and token-VTC lands at 1.00×, indistinguishable from charging milliseconds directly; the curve on the MEASURE tab has its minimum exactly there and rises on both sides.

Which would make this a config bug, except that 15.42 is not a constant. The correct ratio is (iterBase + iterSlope·B) / (B · prefillCost): it is 27.92 at a batch of 8 and 12.29 at a batch of 48, because the fixed per-iteration overhead is amortised over however many sequences happen to be resident. The right value of the constant is a function of the load, and the load is what the scheduler is deciding. Drop the offered load to 0.6× fair share and the measured cost of a decode token rises from 0.93 ms to 4.46 ms — a factor of 4.8 — because a lone sequence occupies the whole GPU for a whole iteration.

The repair is therefore not a better constant. It is to delete the constant: charge the counter dt / B per resident sequence per iteration, which the engine already knows because it just did the iteration. That version scores 1.00× at every flood setting, at every spread setting, and it delivers 93,932 decode tokens against FIFO's 92,864 — better on both axes, which is the only genuinely dominant point on the page.

A perfect version of the obvious fix still fails

The obvious fix costs three lines and no counters: cap each tenant at maxBatch / n = 6 running sequences. Under full backlog every tenant holds its six slots at all times, so every tenant gets exactly a quarter of every decode iteration. And it does: decode time splits 24.7 / 25.2 / 25.2 / 24.9, a ratio of 1.023. It is exactly, provably fair in the thing it controls.

It scores 1.92× overall — worse than doing nothing — because prefill is 31.3% of this machine and the cap says nothing about it. Six slots of 24-token answers turn over fifteen times faster than six slots of 354-token answers, so the classify tenant runs fifteen times as many prefills and burns 18.2% of the whole replica on them against the agent tenant's 1.3%. The mechanism is exact, the fairness is exact, and the resource it was never told about is a third of the machine.

There is a second joke hiding in the cap. Try every setting: 1 slot gives 1.34× and collapses throughput to 37,101 tokens; 6 slots — the only value where four tenants × the cap exactly equals the batch — gives its worst result at 1.92×; and 8 slots gives 1.21×, which looks like a fix and is not, because 4 × 8 = 32 exceeds the batch of 24 and the cap simply never binds. Every setting of the knob that improves the number does so by switching the mechanism off.

The quota denominated in tokens does not save you either

Real APIs meter in tokens per minute, and they charge prompt + max_tokens at admission, because that is the only token count that exists before generation. Give every tenant the identical quota expressed both ways — the page sets the token bucket to exactly rpm × (prompt + default max_tokens), so at the default the two quotas are the same quota — and they produce the same split to two decimal places: 6.87× both. A token quota where everybody sends the SDK's default max_tokens=1024 is a request quota wearing a different unit.

Slide the honesty dial and TPM does start working: at fully honest declarations the split goes 6.87 → 1.26. But look at what had to happen. The declared maxima become 71 / 142 / 569 / 1138 — every client has to size its own ceiling to its own typical answer, which means the fairness of a multi-tenant replica now rests on a field set by the tenants, in their code, in their interest to inflate. It is not free either: answers cut off by the ceiling go from 16 to 67 out of 1,294, a truncation rate of 5.2%. You bought fairness with a field you do not control and paid for it in clipped answers.

Throughput has no single number, and the ranking flips on the unit

Same GPU. Same 120 seconds. Same bill. The requests-per-minute quota delivers 102,765 decode tokens and 697 completed requests. FIFO delivers 92,864 decode tokens and 1,353 completed requests. Counted in tokens the quota wins by 10.7%; counted in requests it loses by 48.5%. It is not a paradox — the unfair schedulers admit fewer, longer requests, so they spend 15.5% of the machine on prefill instead of 28.1% and convert the difference into decode — but it means an operator optimising tokens per second is being paid, in the only currency their dashboard reports, to starve their smallest tenant.

The same inversion shows up in the one fairness statistic that is easy to collect. Rank all nine schedulers by how equal their admissions are, rank them again by how equal their service is, and the two orders have a Spearman correlation of −0.82. The most egalitarian admitter on the page — the token quota, at 1.02× — is the least egalitarian server, at 6.87×. The fair scheduler that works has the second most lopsided admission counts of the nine. If your fairness dashboard counts requests, it is anti-correlated with the thing you meant.

What actually survives contact with the measurement

  • Pick the denominator first. Fairness is not a property of a scheduler; it is a property of a scheduler and the quantity it equalises. Every policy on this page is exactly fair in something.
  • The only denominator that is not an assumption is the one the machine actually spends: dt / B, charged as it is spent.
  • Anything charged at admission — requests, prompt tokens, max_tokens — is a forecast of a number the model has not produced yet.
  • Check whether your tenants are backlogged before you argue about fairness. At 0.6× fair share nothing is queued, and FIFO, round-robin, the work-conserving cap and both VTCs return bit-identical results — while the two quota policies destroy 14.6% of the throughput throttling a machine nobody was competing for.
  • Report the split, not the summary. Jain's index reads 0.676 where the ratio reads 6.87; a four-tenant fleet where one tenant gets a seventh of what another gets still looks like “0.68” on a chart that tops out at 1.

What this page does not model

No language, no quality, no accuracy: an output length is drawn from a distribution and the tokens are counted, never generated. One replica, no routing across replicas, no heterogeneous hardware, no priority classes or paid tiers, no chunked prefill (a prefill stalls the whole batch here, which is the pessimistic case and the one that makes the slot cap's prefill leak visible). Preemption is by recompute, LIFO, and the tokens it throws away are still charged to the tenant that consumed them, because they did consume them. Arrivals are Poisson and lengths are geometric, which is kinder than reality on both tails. Every number on the MEASURE tab is the mean of five independent worlds of 120 simulated seconds; the four sweep charts use three worlds so the page stays interactive, and say so.

🔨 How it is built

The engine is one function. A replica with a running batch, a queue per tenant, and a policy that answers exactly one question: when a slot is free, whose request goes in? Everything else — the fairness, the throughput, the inversion — falls out of that one choice repeated a few thousand times.

1. The machine

Continuous batching: sequences join and leave the batch between iterations rather than waiting for the slowest member. One iteration advances every resident sequence by one token and costs iterBase + iterSlope·B milliseconds, so per-sequence cost falls as the batch grows — that single fact is what later makes the VTC weight load-dependent. A prefill costs prefillCost per prompt token and is added to the iteration that admitted it, stalling everyone. 

const B  = running.length;
const dt = iterBase + iterSlope*B + prefillCost*prefillTokensAdmittedThisStep;
const perSeq = (iterBase + iterSlope*B) / B;        // what one decode token costs the machine
for (const v of running){ v.gen++; gpu[v.tenant] += perSeq; }
t += dt;

perSeq is the whole accounting system. Summed over every iteration and every resident sequence it comes to exactly the busy time, so the four tenant shares add to 1.000000 — the self-test asserts it to 1e-9. There is no separate model of “capacity”: the machine is 120 seconds long and the only question is how it gets divided.

2. The KV cache, and preemption that costs something

A resident sequence holds prompt + generated tokens of cache, so the pressure grows as the batch decodes. When it would overflow, the most recently admitted sequence is evicted, its generated tokens are thrown away, and it goes back to the front of its tenant's queue to be re-prefilled. The discarded work is still charged to the tenant that consumed it, which is the honest accounting and also the reason a fairness policy cannot fix its own mistakes for free.

3. Nine policies, one function

Each is a rule for picking a tenant from those with a queued request that fits:

  • fcfs — the oldest waiting request anywhere.
  • rr — a rotating cursor over tenant queues, skipping empty ones.
  • rpm — a token bucket of requests per tenant; ineligible tenants wait, and among the eligible it is FIFO.
  • tpm — the same bucket denominated in tokens, charged prompt + declared max_tokens at admission, sized so that at the default declaration it is arithmetically the same quota as rpm.
  • cap / capwc — a hard limit on running sequences per tenant; the second variant lets a tenant exceed it when nobody else is waiting.
  • vtc — lowest virtual counter, where the counter accrues w_p per prompt token and w_o per generated token as service is delivered, plus the lift rule on a tenant that returns from idle.
  • vtcNoLift — the same, with the lift rule removed, so an absent tenant banks a deficit.
  • vtcGpu — the same, with dt / B in place of the two weights.

4. The worlds are built once, before the policy is chosen

Every arrival — its time, its prompt length, its output length — is drawn from a per-tenant mulberry32 stream seeded from the world seed and the tenant index, before any scheduling happens. Changing the policy cannot change the workload, and changing one tenant's parameters cannot shift another tenant's random stream. Without that, every comparison on the page would be a comparison of two different worlds.

5. Equal cost is structural, not a correction

Each configuration gets one replica for 120,000 simulated milliseconds. There is no budget to normalise and no price to divide by: the bill is the same because the machine is the same machine for the same time. A policy that “wins on throughput” won by taking the machine away from somebody, and the table shows exactly whom.

6. Two closed forms that let the simulation be checked

When every tenant is backlogged, two predictions can be written down without simulating anything, and both are asserted against the engine: 

// any policy that equalises ADMISSIONS gives service in proportion to per-request cost
cost_i  = prefillCost*promptMean + outMean_i * perSeq(maxBatch)
share_i = cost_i / sum_j cost_j                     // 6.9 / 10.2 / 29.9 / 52.9 %

// FIFO gives service in proportion to OFFERED LOAD
share_i = offer_i / sum_j offer_j                   // 25 / 25 / 25 / 25 % by construction

// the weight at which a weighted-token counter equals a millisecond counter
wStar   = (iterBase + iterSlope*B) / (B * prefillCost)   // 15.42 at B = 24

The first predicts the quota's measured 7.4 / 11.3 / 30.3 / 51.0 to within a point and a half; the second predicts FIFO under a flood of 8× to within four points; the third predicts, to two decimal places, where the wo curve has its minimum. A simulation that only agrees with itself has not been checked.

7. The self-test

Roughly 120 assertions run in the page on load: conservation (shares sum to one, admissions equal completions plus residents, every policy gets the same busy time), the closed forms, the declared corners (spread 0 makes every policy fair; a slot cap at or above the batch is FIFO; no contention makes five policies bit-identical), determinism of the world builder, the monotonicity of each sweep, and the specific measured claims quoted in the headline. A separate Node verifier re-runs the same engine against an independently written reference simulator over several hundred configurations.
