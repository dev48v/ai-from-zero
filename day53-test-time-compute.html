AIFromZero · Day 53

🧮 Test-Time Compute — spend more compute at answer time to get a better answer, without training a bigger model. A single sample from a model is a noisy guess: on a hard question it is right only part of the time. The insight behind inference-time scaling is that you can trade extra compute at inference for accuracy. Draw the model's answer N times instead of once and aggregate: self-consistency takes the majority vote across the samples, and best-of-N uses a verifier to keep the single best one. Or let the model "think longer" — o1 and DeepSeek-R1 spend thousands of hidden reasoning tokens exploring, checking, and backtracking before committing, which is search inside one long chain of thought. Accuracy climbs with compute — steeply at first, then it plateaus (diminishing returns), and the two methods plateau in different places: majority vote can never beat the fraction of questions the model is right about on average, while best-of-N keeps climbing toward 100% because it only needs one correct sample the verifier can spot. This trades off against pretraining scale: a small model given a big test-time budget can match a much larger model answering once — sometimes it's cheaper to think harder than to train bigger. Slide the compute budget up and watch the accuracy curve climb and level off — no network, a baked-in probability model, deterministic and reproducible.

Test-time compute buys accuracy at inference instead of at training. Self-consistency (majority vote over N samples) is verifier-free but plateaus at the fraction of questions the model is right about on average — it can even lock in a confident wrong answer. Best-of-N keeps climbing toward 100% because a verifier only needs one correct sample among the N — but it needs a verifier, and a weak verifier caps the gain. Both curves are concave: the first extra samples help a lot, later ones barely move the needle — that's the compute–accuracy tradeoff. And it trades against pretraining scale: a small model with a big test-time budget can match a bigger model answering once, which is why o1 / DeepSeek-R1 "think longer" and why labs now scale inference compute, not just parameters.

    One sample is a coin-flip on hard questions
    
        
    Model each question by its single-sample accuracy p — the probability one sampled answer is correct. Easy questions have p near 1; hard ones sit below 0.5, so a single guess is more often wrong than right. This p is what a real model gives you when you sample at temperature > 0.
    
        
    import random

# 12 toy questions, each with its own single-sample accuracy p.
# (In reality p comes from the model itself, sampled at temperature > 0.)
QUESTIONS = [0.92, 0.85, 0.78, 0.70, 0.62, 0.58,
             0.54, 0.48, 0.42, 0.35, 0.25, 0.15]

def one_sample(p: float) -> bool:
    "A single sampled answer: correct with probability p."
    return random.random() < p

# Single-sample accuracy of the whole set = just the average p.
baseline = sum(QUESTIONS) / len(QUESTIONS)      # ~0.55 — barely a coin flip

    Spend compute: draw N samples instead of one
    
        
    Test-time compute means calling the model N times on the same prompt at temperature > 0, so each call is an independent draw. N is the compute budget — cost and latency scale roughly linearly with it. The whole game is turning those N noisy draws into one better answer.
    
        
    def draw_samples(question, n, temperature=0.8):
    "Call the model n times on the same prompt — n independent guesses."
    return [sample_answer(question, temperature) for _ in range(n)]

# With a real model this is n API calls (or one call with n=... where supported):
#   client.messages.create(model="claude-opus-5", messages=[...])  # x N
# Cost & latency grow ~linearly in n — that's the compute you're spending.

    3
    Self-consistency — take the majority vote
    
        
    The cheapest aggregation (Wang et al., 2022): draw N samples, keep the most common answer. No verifier needed. Analytically, if the correct answer beats the model's favourite wrong answer with probability p, majority-vote accuracy is the binomial tail P(correct votes > N/2). That rises toward 1 when p > 0.5 — and toward 0 when p < 0.5, because voting only amplifies whatever the model believes most often.
    
        
    from collections import Counter
from math import comb

def majority_vote(samples):
    "Self-consistency: the answer that appears most often wins."
    return Counter(samples).most_common(1)[0][0]

def majority_accuracy(p, n):
    "P(correct is the majority) for a binary correct-vs-wrong contest."
    acc = 0.0
    for c in range(n + 1):                       # c = # correct votes
        pm = comb(n, c) * p**c * (1 - p)**(n - c)
        if   2 * c >  n: acc += pm               # correct wins
        elif 2 * c == n: acc += 0.5 * pm         # tie, break 50/50
    return acc
# p=0.62, n=1 -> 0.62 ; n=15 -> 0.84 ; n=63 -> 0.94  (climbs, then plateaus)
# p=0.42, n=63 -> ~0.10  (LOCKS IN the wrong answer — voting can't save it)

    Best-of-N — let a verifier keep the best sample
    
        
    If you have a verifier — a reward model, a unit test, a checker — you don't need the majority; you need one good sample the verifier can recognize. With a perfect verifier, accuracy is 1 − (1 − p)N (a.k.a. pass@N): the chance that at least one of N samples is correct. That climbs toward 1 for any p > 0 — it fixes even the hard questions majority vote gives up on. The catch: a real verifier is imperfect, and its accuracy caps the gain.
    
        
    def best_of_n(samples, verifier):
    "Keep the sample the verifier scores highest."
    return max(samples, key=verifier)

def best_of_n_accuracy(p, n):
    "pass@N with a perfect verifier: P(at least one of n samples correct)."
    return 1 - (1 - p) ** n
# p=0.42, n=1 -> 0.42 ; n=8 -> 0.98 ; n=16 -> 0.9997
# One correct sample is enough — the verifier finds the needle in the haystack.
# Reality check: a verifier with accuracy v < 1 caps this well below pass@N.

    The accuracy-vs-compute curve — and why it plateaus
    
        
    Sweep N and average over the question set — exactly the LOOK chart. Both curves are concave: the first few extra samples buy a lot of accuracy, later ones almost nothing (diminishing returns). Plotting N on a log axis makes the tail visibly flatten. The gap between the two plateaus is the value of having a verifier.
    
        
    def curve(questions, strategy, budgets):
    acc_fn = {"majority": majority_accuracy,
              "best_of_n": best_of_n_accuracy}[strategy]
    return {n: sum(acc_fn(p, n) for p in questions) / len(questions)
            for n in budgets}

budgets = [1, 2, 4, 8, 16, 32, 64]
print(curve(QUESTIONS, "majority",  budgets))  # 0.55 -> ~0.66 then flat
print(curve(QUESTIONS, "best_of_n", budgets))  # 0.55 -> ~0.98, keeps climbing
# Majority plateaus below 100% (bounded by the frac. of questions with p>0.5);
# best-of-N keeps climbing because it only needs one correct sample per question.

    "Think longer" — search inside one chain of thought (o1 / R1)
    
        
    Sampling-and-voting is parallel test-time compute. o1 and DeepSeek-R1 add sequential test-time compute: one long chain of thought that explores, self-checks, and backtracks before answering — thousands of hidden reasoning tokens. It's implicit search inside a single sample, and it's exposed as a simple knob rather than an N-of-samples loop.
    
        
    import anthropic
client = anthropic.Anthropic()

# Claude: adaptive thinking + an effort knob = "how long to think".
msg = client.messages.create(
    model="claude-opus-5", max_tokens=8000,
    thinking={"type": "adaptive"},          # let the model decide how much to think
    output_config={"effort": "high"},       # low | medium | high | xhigh | max
    messages=[{"role": "user", "content": "Prove or disprove: ..."}],
)

# OpenAI o1 exposes the same idea as reasoning_effort:
#   client.chat.completions.create(model="o1", reasoning_effort="high", ...)
# DeepSeek-R1 emits a long <think>...</think> trace before the final answer.
# More thinking tokens = more test-time compute = better answers on hard problems.

    Test-time compute vs training a bigger model
    
        
    The tradeoff DeepMind made concrete (Snell et al., 2024): on many problems, giving a small model more test-time compute beats using a much larger model that answers once — up to a point. A bigger base model raises every sample's p, which shifts the whole curve up (bump the model size in LOOK to see it). So the question isn't "bigger or think-harder" — it's how to split a fixed budget between the two.
    
        
    # A bigger base model raises single-sample accuracy p on every question.
def scale_params(questions, boost):           # "boost" ~ more pretraining
    return [min(p + boost, 0.985) for p in questions]

small = QUESTIONS                              # small model, cheap per sample
large = scale_params(QUESTIONS, boost=0.15)   # big model, expensive per sample

# small model + N samples  vs  large model + 1 sample, at matched FLOPs:
small_ttc = curve(small, "best_of_n", [16])[16]   # think harder
large_1x  = sum(large) / len(large)               # train bigger, answer once
# Often small_ttc >= large_1x — cheaper to add inference compute than params.
# Compute-optimal test-time scaling picks N per question by difficulty.

    In practice — the real toolkit
    
        
    You rarely hand-roll all of this. Reasoning models (o1, o3, DeepSeek-R1, Claude with extended thinking / effort) bake sequential test-time compute into the model. For parallel scaling, sample N completions and aggregate — majority vote for free-form reasoning, or a trained reward model / process reward model for best-of-N. Serving stacks (vLLM, SGLang) make the N parallel samples cheap.
    
        
    # Parallel test-time compute with any chat model: self-consistency in ~10 lines.
from collections import Counter

def self_consistent_answer(client, prompt, n=16):
    outs = [client.messages.create(
                model="claude-opus-5", max_tokens=2000,
                messages=[{"role": "user", "content": prompt}],
            ).content[0].text
            for _ in range(n)]
    finals = [extract_final_answer(o) for o in outs]   # your parser
    return Counter(finals).most_common(1)[0][0]        # majority vote

# Sequential test-time compute: just pick a reasoning model + turn the knob up.
#   Claude:   effort="xhigh" / adaptive thinking
#   OpenAI:   model="o3", reasoning_effort="high"
#   DeepSeek: model="deepseek-reasoner"  (R1-style long CoT)
# Best-of-N with a verifier: score N samples with a reward model, keep argmax.
