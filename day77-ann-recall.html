And the other direction: hold the recall and read off the bill. The cell knob cannot even land on a target — there is nothing between one cell and the next, so a team that wants a stated recall buys the first setting that clears it and pays for the overshoot.

Stopping on a bound instead of on a count

There is a rule that fixes the recall exactly. Every member of a cell is at least as far from the query as the cell’s centroid is, minus the cell’s radius — that is the triangle inequality and nothing else — so once that lower bound clears the k-th best distance already in hand, no unopened cell can hold a better neighbour and the search is finished. The page checks that against brute force one query at a time, and the check is an identity: the two result lists must be the same list.

What it costs is a tail. Exactness has no fixed price, and the price it does have is set by the query, so a latency budget has to cap it — and the cap is the only thing on this page that can make the rule wrong.

The order that makes the stop safe is the wrong order to truncate

The bound rule cannot walk the cells by centroid distance. A large loose cell can sit behind a small tight one under that order, so the first cell that fails the test is not the last one that would — the search has to walk by the bound itself. That is a different order, and truncating it at a fixed number of cells is worse than truncating the ordinary one. The recommendation and the algorithm want opposite things.

The control

What is actually being measured

Everything on this page comes out of four declared objects and nothing else.

  • A document is a point on the unit sphere. It belongs to one of a handful of topics and sits near that topic’s direction, with a spread that differs from topic to topic — one subject written about in fifty near-identical documents, another sprawling. There is no text anywhere in the engine, because none is needed: an index sees coordinates.
  • A query is built from a document, and that document is the answer. It is the only thing on the page that knows what the right answer is, and no part of the index is allowed to see it.
  • An index is a partition. k-means splits the corpus into cells, each with a centroid and a radius; a search sorts the cells by distance to their centroid and opens some of them. That is the whole of what an inverted-file vector index does, and every real one adds compression on top of exactly this.
  • A cost is one number: how many distance computations were performed, centroids included. Brute force costs the size of the corpus. Every comparison on this page is made at an equal cost or an equal recall, never at an equal setting, because a setting is not a quantity.

Why a count is the wrong unit

k-means does not make cells of equal size. It makes cells of roughly equal spread, so a tight topic gets many small cells and a diffuse one gets a few large ones. nprobe = 4 therefore means “scan four cells” and not “scan four cells’ worth of work”: for a query landing beside a tight topic it can be a few dozen documents, and beside a diffuse one several hundred.

The direction of the resulting error is the uncomfortable part, and it is not an accident. A tight topic is exactly where a query’s ten nearest neighbours are spread across many cells, because the region has been finely cut. So the query that most needs cells opened is the query for which four cells is least work, and the query that needs one cell gets four large ones. The correlation between what a query costs and how well it is served is positive, which is the wrong sign for a budget.

Nothing about this depends on k-means specifically. Any partition that adapts to density produces cells of unequal population, and any budget denominated in cells inherits the same mismatch. A graph index has the same problem in a different currency: ef is a count of candidates, not of edges walked.

Why the bound is exact, and why it needs its own order

For any member x of cell c, the triangle inequality gives dist(q,x) ≥ dist(q,centroidc) − radiusc, where the radius is the distance from the centroid to its own farthest member. That right-hand side is computable before the cell is opened. If it already exceeds the k-th best distance in hand, the cell cannot improve the result, and neither can any cell whose bound is larger.

That last clause is the whole subtlety. The rule licenses stopping only if the cells are walked in order of the bound. Under the usual order — by centroid distance — a large loose cell can sit behind a small tight one, so the first cell that fails the test is not the last one that would, and stopping there quietly drops neighbours. The first version of this page did precisely that and was exact on 99.38% of queries, which is the tell: a rule that is provably exact does not have a hit rate.

What went against the build

What this does not model

  • Compression. Real indexes quantise the vectors as well as partition them, which adds a second, different kind of error: distances become approximate everywhere rather than absent in places. It moves every number here and it moves none of the arguments, because a compressed index still budgets in cells.
  • Graph indexes. A navigable small-world graph fails differently — it gets stuck rather than skipping a region — but it is budgeted the same way, by a count that is not a unit of work, and the same fix applies to it.
  • Updates. The corpus here never changes. A live index drifts away from its own centroids as documents arrive, which makes the cells worse over time in a way no query-time knob can see.
  • Cache and memory locality. Distance computations are counted as if they all cost the same. On real hardware a contiguous cell is much cheaper per document than a scattered one, which changes the exchange rate between the policies without changing their order.
  • The embedding itself. The last table is the only place the embedding’s own quality appears, and it appears as a declared knob. Everything else on this page holds it fixed on purpose, so that no result can be smuggled in from it.
  • Filtered search. A metadata filter applied after retrieval interacts violently with everything here, because it removes documents from a list that was already short. It deserves its own page.
