AIFROMZERO · DAY 67

🧭 Embedding model migration — a better embedding model is free to adopt and expensive to install. You have to re-embed the whole corpus, and for the days or weeks that takes, half your index is in one vector space and half in another. A cosine computed across that seam is not a weak signal, it is no signal — the two models' axes have nothing to do with each other. This page builds the real cost/quality frontier of a half-finished migration, priced in embedding calls. The measured headline: with a random re-embedding order and the new query encoder already live, recall bottoms out 44 points below the index you started with, and you must re-embed 60% of the corpus before search is merely back to where it was. Then the twist that cost me the page I meant to write: the fix is not the clever one. Normalising scores across the two spaces is worth less than simply re-embedding in traffic order — and at an equal budget the normalisation can make things worse. Pure vanilla JavaScript, one file, offline.

SELF-TEST

running…

Two embedding models do not disagree. They are unrelated.

A newer embedding model comes out, it scores better on your evals, and adopting it is a one-line change. Then you remember the index. Every vector in it was produced by the old model, and a vector is only meaningful relative to the model that made it — the axes are whatever that particular training run happened to land on.

So a cosine between a new-model query and an old-model document is not a slightly degraded score. It is a number drawn from noise: mean about zero, and a spread as wide as a real similarity, so with a few hundred documents plenty of them out-score the right answer by luck alone. Ranking 400 documents by it finds the answer 2.7% of the time, against 2.5% for picking ten out of four hundred at random and 66% for an index whose vectors match its query encoder.

score(query_new, doc_new) = real similarity
score(query_new, doc_old) = noise            <- the seam

That number has to be averaged over several draws to be worth anything, and it is a good illustration of why. One particular pair of random projections in this simulation gets lucky and reaches 10.7% — still a sixth of a working index, but six times chance. Two independently trained embedding spaces are not guaranteed to be exactly orthogonal to one another; they are only guaranteed to be useless to each other, which is a weaker and more annoying property.

The valley

Re-embedding 100,000 documents is not instant. For the duration you have a mixed index, and what you do about the query side decides how bad that is. The tempting move is the simple one: point the query encoder at the new model and let the re-embedding job catch up. Every document it has not reached yet is now scored by noise.

Measured on this page, with a random re-embedding order: recall falls from 0.61 on the un-migrated index to 0.17 when 5% of the corpus has been converted, and does not climb back above the starting point until 60% of the corpus is done. The migration is not a slow improvement. It is a long hole with the improvement at the far end.

The shape is easy to see once you write it down. A query whose answer has been re-embedded is fine. A query whose answer has not been re-embedded is answered by noise. So recall tracks the fraction of traffic whose answers are converted — not the fraction of documents. Those two numbers are only equal if you convert documents in an order uncorrelated with demand.

Which is the actual lever

Query traffic is Zipf-shaped. A small head of documents absorbs most of the queries. In the simulation, re-embedding the most-queried 30% of documents covers 81% of the query traffic; a random 30% covers 27%, which is to say exactly 30% and nothing more.

So the cheapest possible intervention — sort the re-embedding job by query count — turns the valley into a step. It is worth being precise about what it fixes: the hole is exactly as deep either way, because the moment you point the query encoder at the new model and no document has been converted yet, search is broken regardless of what order you plan to convert them in. What ordering changes is how long you stay down there. Hot-first is back to even at 10% of the corpus against 60% for a random order — it spends 10% of the migration under water instead of 57%.

The fix I expected, and what it actually did

The sophisticated answer is to keep both encoders alive during the migration: embed each query twice, score every document in its own space, and merge. That removes the seam — no score is ever computed across spaces. It costs one extra query embedding per request.

It works, and it is not the biggest lever, and there is a sting in it. Merging raw cosines from two spaces is not fair, because the better model produces higher similarities for related documents and — if it is more anisotropic — higher similarities for everything. At 30% converted, the migrated documents take 62% of the top-10 slots rather than 30%. Z-scoring each space's candidates before merging restores the fair share almost exactly.

And then the measurement contradicted the recommendation. Under hot-first ordering the biased merge scores higher than the fair one — 0.897 against 0.873 — because the documents it unfairly favours are precisely the popular ones the queries are looking for. Correcting the bias throws away a shortcut that happened to be pointing the right way. Under a random order, where the favoured documents are a random sample, the correction is worth a clear 8 points. The normalisation is not right or wrong; it is right exactly when your migration order is uncorrelated with your traffic.

The economics: a bridge, not a destination

Price everything in embedding calls. Re-embedding a fraction f of a D-document corpus costs f·D, once. A second query-side encoder costs one extra call on every query, for as long as the migration runs — Q calls over a window of Q queries.

f·D + 2Q   vs   D + Q          =>   break-even at Q = D·(1 − f)

At a 100k-document corpus and a half-finished migration, the dual-encoder bridge is the cheaper plan for the first 50,000 queries and the more expensive one thereafter. That is the whole decision, and it is one line of arithmetic that almost nobody does before choosing.

The equal-cost comparison on the page is blunter still. 150,000 calls buys either a finished re-index served by one encoder — recall 0.973 — or a half-finished one served by two, at 0.917. At the same spend, finishing wins. The dual-encoder trick is not a way to avoid the re-index. It exists so the weeks in the middle do not show up as an outage.

What to do on a real system

  • Never swap the query encoder first. It is the one-line change, and it is the one that produces the valley.
  • Sort the backfill by query count. Free, and worth more than anything else on this list.
  • Write to both indexes on ingest from the day you decide to migrate, so the backlog stops growing while you work through it.
  • Cut over per-shard, not per-document if you can — a shard that is entirely in one space has no seam inside it at all.
  • If you must merge across spaces, normalise per space — z-scores or rank fusion — and know that you are giving up a bias that may have been helping you.
  • Version the vectors. A document row that does not record which model produced its vector makes every one of these decisions unavailable to you.

🔨 How it is built

1. Two encoders, one meaning

// each document has a latent MEANING. An encoder is a random projection of it,
// plus that encoder's own noise. Two encoders drawn independently produce spaces
// whose axes have nothing to do with each other.
const sig = unit(A · latent);                       // A is this encoder's projection
vec = unit(sig + sigma·noise + anisotropy·common);  // `common` is the space's shared lean

Nothing here simulates a model's language ability. It simulates the only property that matters for a migration: that the two spaces are incomparable, and that one of them is less noisy than the other.

2. Three score matrices, computed once

Sold[q][d] = cos(query_old, doc_old)     // the index you have
Snew[q][d] = cos(query_new, doc_new)     // the index you want
Sx[q][d]   = cos(query_new, doc_old)     // the seam

Every strategy and every migration fraction is then a selection over these three, so the whole frontier costs one pass of vector arithmetic rather than one per point. That is what makes the sliders interactive.

3. Four ways to score a half-migrated index

naive : flags[d] ? Snew : Sx          // you swapped the query encoder
dual  : flags[d] ? Snew : Sold        // both encoders alive, raw cosines merged
dualz : z-score each space over its own candidates, then merge
split : one consistent index per query — the no-seam reference

split is a reference line, not a purchasable plan: it asks what recall would be if the seam did not exist. Worth noting that dual sometimes beats it, which is not a bug — deflated old-space scores make life easier for a query whose answer is already migrated.

4. Cost is embedding calls, and the frontier is drawn in them

planCost(f, docs, queries, encoders) = f·docs + encoders·queries
breakEvenQueries(f, docs)            = docs · (1 − f)   // f·D + 2Q == D + Q

The x-axis of the chart is that cost, which is why the two-encoder curves start half a corpus to the right. Comparing them anywhere except along a vertical line is meaningless, and putting cost on the axis is the only way to keep that honest.

5. A degeneracy check, learned the hard way

The previous page in this series had a model that collapsed to exact 0/1 scores at its extreme setting, which made a quantile threshold land on a tie and quietly measured the whole effect as zero. So this engine is tested at its extremes too: at maximum encoder quality and maximum anisotropy the score row still has 400 distinct values out of 400 and a standard deviation above 0.2. Real similarity scores are continuous, and a simulation whose scores are not will lie to you at exactly the settings you were most curious about.

6. What the tests pin

// the seam really is noise, not a weak signal - averaged over five worlds, because
// one pair of random projections can get lucky and the claim must not rest on it
assert(|mean(crossSpaceScores)| < 0.05);
assert(stdev(crossSpaceScores) > 0.15);          // and NOT collapsed

// THE valley

// and order is the lever

The one worth having is the tenth. It says the tidy recommendation is wrong under the ordering you should already be using, and it is in the test file so nobody can quietly delete the inconvenient half of the finding later.
