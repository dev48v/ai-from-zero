AIFromZero · Day 56

🥇 Rerankers — retrieval gets the right documents into the pile; a reranker gets them into the right order. The retriever every RAG system starts with is a bi-encoder: it turns the query into one vector and each document into one vector independently, then ranks by cosine similarity. That is gloriously fast — the document vectors are computed once, offline, and an approximate-nearest-neighbour index searches millions of them in milliseconds — but it pays for that speed with a blind spot: each document is squashed into a single vector before it ever sees the query, so the score can't reflect how the query and that specific document actually interact. The result is strong recall (the useful docs are somewhere in the top-N) but coarse precision at the very top: a doc that merely shares a lot of surface words can out-rank the doc that truly answers the question. A reranker is a second, slower, sharper stage. It's a cross-encoder: it feeds the (query, document) pair together through the transformer so every query token can attend to every document token, and emits one calibrated relevance score per pair. Far more accurate — but there's nothing to precompute (the score depends on the query), so you can't run it over a whole corpus. The pattern that makes it practical is retrieve-then-rerank: let the cheap bi-encoder fetch a broad top-N shortlist, then spend the expensive cross-encoder only on those N pairs, and reorder to a precise top-k. Below is a live, fully self-contained demo over a baked-in help-centre corpus — a real TF-IDF bi-encoder for stage 1 (fast but coarse, and it does mis-rank a keyword-stuffed decoy to the top) and a deterministic canned cross-encoder for stage 2 that reads each pair jointly and pulls the genuinely-relevant answer up to #1. Pick a query, slide the top-N cut, and watch the two rankings side by side with every moved position flagged. No API, no LLM, all deterministic.

Retrieve broad and fast, then rerank the shortlist for precision.

Nine help-centre articles are the corpus. Stage 1 is a real bi-encoder (TF-IDF + cosine) that scores every doc against the query independently — fast, but it rewards surface word-overlap, so a keyword decoy lands at or near the top and the true answer sits lower. Stage 2 is a cross-encoder that re-reads each (query, doc) pair jointly and re-scores only the top-N shortlist, reordering it so the true answer rises to #1. Everything is deterministic and runs in your browser — no network, no embedding API, no LLM.

A reranker doesn't retrieve — it re-orders. The bi-encoder's job is recall: sweep a huge corpus in milliseconds and make sure the good docs are somewhere in the top-N. The cross-encoder's job is precision: read each shortlisted (query, doc) pair together and decide which one truly answers the question, promoting it past the docs that only looked relevant. Because it runs on N pairs instead of millions, the extra accuracy costs a bounded amount of latency — and because it can only reorder what stage 1 surfaced, N must be large enough for recall. This demo uses TF-IDF and a canned scorer, but the two-stage shape — fast bi-encoder for recall, slow cross-encoder for precision — is exactly how Cohere Rerank, bge-reranker and the MS-MARCO cross-encoders slot into a real RAG pipeline before the answer ever reaches the LLM.

🔨 Build retrieve-then-rerank — bi-encoder recall, cross-encoder precision

    
Reproduce the LOOK engine as real code: a fast first-stage retriever fetches a broad top-N, a cross-encoder re-scores each (query, doc) pair jointly, and you reorder the shortlist so the truly-relevant doc lands on top. The toy uses TF-IDF for stage 1 and a keyword-blind heuristic for stage 2; the last block swaps in a real cross-encoder / Cohere Rerank and hands the top-k to Claude. Every block is the exact idea flowing through LOOK.

    The corpus and a query
    
        
    A retriever ranks a fixed corpus against a query. In the real world the corpus is millions of chunks in a vector store; here it's a handful of help-centre articles so you can see every score.
    
        
    corpus = [
    "On the log in page tap the recovery link and we email a fresh code...",   # reset access (the true answer)
    "Password security tips: if you forgot a password, still pick a strong...", # keyword decoy
    "Two factor authentication adds a one time code from your phone...",
    # ...more articles...
]
query = "why can't I log in - I forgot my password"

    Stage 1 — the bi-encoder: embed query & docs separately
    
        
    A bi-encoder maps the query and each doc to one vector each, independently. The doc vectors are computed once and stored, so retrieval is just a cosine / nearest-neighbour lookup — millions of docs in milliseconds. The demo uses a TF-IDF bag-of-words; production uses a neural embedder, but the shape is identical.
    
        
    from sentence_transformers import SentenceTransformer, util

bi = SentenceTransformer("all-MiniLM-L6-v2")     # a bi-encoder
doc_emb = bi.encode(corpus, convert_to_tensor=True)   # PRECOMPUTED, offline
q_emb   = bi.encode(query,  convert_to_tensor=True)

# cosine every doc against the query, keep the broad top-N
scores = util.cos_sim(q_emb, doc_emb)[0]
topN   = scores.topk(N).indices.tolist()          # a shortlist, fast

    3
    The blind spot: high recall, coarse top-order
    
        
    Because each doc is squeezed into a vector before it sees the query, the bi-encoder can't model how this query interacts with this doc. A doc that just repeats the query's words (the keyword decoy) can out-score the doc that actually answers it. The right docs are in the top-N (good recall) — but the #1 is often wrong (poor precision).
    
        
    # bi-encoder top-3 for "forgot my password":
#   1. "Password security tips..."   <- decoy: repeats 'password' x5
#   2. "On the log in page tap the recovery link..."  <- the real fix
#   3. "Two factor authentication..."
# recall is fine (the answer is in the list) but the ORDER is wrong.
# no prompt tweak downstream can undo a bad #1.

    Stage 2 — the cross-encoder: score the pair jointly
    
        
    A cross-encoder concatenates [query] [SEP] [doc] and runs the pair through the transformer together, so every query token attends to every doc token. It outputs a single relevance logit. Nothing can be precomputed — the score depends on the query — which is exactly why it's accurate and why you only run it on a shortlist.
    
        
    from sentence_transformers import CrossEncoder

ce = CrossEncoder("cross-encoder/ms-marco-MiniLM-L-6-v2")

# one forward pass PER (query, doc) pair — no offline index possible
pairs  = [(query, corpus[i]) for i in topN]
rel    = ce.predict(pairs)          # e.g. [0.41, 0.96, 0.34, 0.04]
# the pair with the true answer now scores highest, not the decoy

    Reorder the shortlist → precise top-k
    
        
    Sort the shortlist by the cross-encoder score and take the top-k. The doc the bi-encoder buried at rank 2 or 3 is now #1; the keyword decoy drops. This reordered top-k is what the LLM actually reads.
    
        
    order  = sorted(range(len(topN)), key=lambda j: rel[j], reverse=True)
reranked = [topN[j] for j in order]          # global doc ids, best first
topk = reranked[:k]                          # feed these to the LLM

for j in order:
    print(f"{rel[j]:.2f}  {corpus[topN[j]][:60]}")
# highest-relevance pair first -> the true answer leads

    The two-stage pipeline in one function
    
        
    Wrap it up: bi-encoder fetches the broad top-N (recall), cross-encoder re-scores those N pairs (precision), return the reordered top-k. This retrieve-then-rerank shape is the whole pattern.
    
        
    def retrieve_then_rerank(query, N=50, k=5):
    # STAGE 1 — cheap, over the whole corpus
    scores = util.cos_sim(bi.encode(query), doc_emb)[0]
    shortlist = scores.topk(N).indices.tolist()
    # STAGE 2 — expensive, only over N pairs
    rel = ce.predict([(query, corpus[i]) for i in shortlist])
    order = sorted(range(N), key=lambda j: rel[j], reverse=True)
    return [shortlist[j] for j in order[:k]]
# fast recall from stage 1 + sharp precision from stage 2

    Choosing N — the recall ⇄ latency dial
    
        
    The reranker can only reorder what stage 1 surfaced: if the true answer sits at bi-encoder rank 60 and you rerank the top 50, it never gets a chance. Raise N for recall, but each extra doc is another cross-encoder forward pass, so latency grows with N. Typical N is 50–200; measure recall@N on your data and pick the smallest N that still catches the answers.
    
        
    # cost model: 1 ANN lookup (stage 1) + N transformer passes (stage 2)
#   N too small -> answer never reaches the reranker (recall ceiling)
#   N too big   -> pay to re-score docs stage 1 already ruled out
#
# tune empirically:
for N in (10, 25, 50, 100, 200):
    print(N, recall_at_k(eval_set, N=N, k=5))   # pick the knee of the curve

    In practice — a hosted reranker, then answer with Claude
    
        
    In production you rarely host the cross-encoder yourself: Cohere Rerank, Voyage rerank, or an open bge-reranker take the query plus the shortlist and return the reordered docs. The MTEB reranking benchmarks track how much they lift retrieval. Then hand the precise top-k to claude-opus-5 — because the #1 chunk is now the real answer, the model has what it needs.
    
        
    import cohere, anthropic

co     = cohere.Client()
client = anthropic.Anthropic()

# stage 1: your vector DB returns a broad shortlist (top-N)
shortlist = vector_db.search(query, top_n=100)

# stage 2: hosted cross-encoder reranks -> precise top-k
ranked = co.rerank(model="rerank-english-v3.0",
                   query=query, documents=shortlist, top_n=5)
context = "\n\n".join(shortlist[r.index] for r in ranked.results)

msg = client.messages.create(
    model="claude-opus-5", max_tokens=1024,
    system="Answer only from the provided context. Cite the source.",
    messages=[{"role": "user",
               "content": f"Context:\n{context}\n\nQuestion: {query}"}],
)
# the reranked #1 is the true answer -> grounded, correct response

🎉 Day 56 of AIFromZero done.
A reranker is the precision stage that a fast retriever can't be. The bi-encoder embeds query and docs separately for millisecond recall over millions, but squashing each doc to a vector before it sees the query leaves the top-order coarse. The cross-encoder reads each (query, doc) pair jointly for a sharp relevance score — too slow for a whole corpus, perfect for a shortlist. Retrieve-then-rerank combines them: broad top-N for recall, cross-encoder rerank for precision, reorder to top-k before the LLM reads a word. Tune N for the recall/latency tradeoff; reach for Cohere Rerank / bge-reranker in production. 👉 Tomorrow — Day 57: continuing AIFromZero.
