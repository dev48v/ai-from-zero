🔄 Tool-call retries — the tool times out, the agent tries again. Every framework does this and it is the right default for a read. Nothing here simulates language: the engine simulates the CALL — a request that may not arrive, a server that may have applied it anyway, and a reply that may not come back — over 4,000 enumerated timelines per policy, so every figure is a count. The agent sees only the reply; the world knows what actually happened, and the two are compared. 🔴 Turning on retries takes the agent's own success rate from 81.92% to 96.95% while the share of calls that applied exactly once goes DOWN, 89.95% to 89.42%. The metric improves by fifteen points and the world gets slightly worse. 🔴 What paid for it: 334 calls of 4,000 applied more than once, and the agent's success metric cannot see a single one of them — from inside the agent a duplicated write and a clean write are the same event. 🔴 And the fix is invisible too. Adding an idempotency key takes exactly-once from 89.42% to 97.78% and leaves the reported success rate at 96.95%, identical to three decimal places. The change that matters moves no number the agent reports.

Three ways a call fails, and they are not the same failure. The request never arrives — nothing applied. The request arrives, applies, and the reply is lost — applied, and the agent does not know. The server refuses — nothing applied, and the agent does know. Only the middle one makes a retry dangerous, and from the agent's side the first two are indistinguishable.

1. The metric and the world move in opposite directions

Retrying converts reported failures into reported successes, which is exactly what it is for and is genuinely valuable on a read. On a write it also converts some applied-once calls into applied-twice calls, and the agent has no way to count the second kind. The success rate is a measurement of the replies, not of the world.

2. The honest gain, stated plainly

It would be wrong to leave this as “retries are bad”. Without them, the agent reports a failure for a call that actually succeeded — times in 4,000 — the write landed and the reply was lost, so the agent reports failure and, in a real system, whatever it does next is built on a false picture.

Retrying cuts that from — to —. Both problems are real; retries trade one for the other, and the trade is good for reads and bad for writes without an idempotency key.

3. The fix changes nothing the agent can see

🔴 An idempotency key does not prevent the retry and does not change the reply the agent gets. It stops the second application. So the reported success rate is identical with and without it — the same number, from the same 4,000 timelines — while duplicate applications go from — to 0. Any evaluation that scores an agent on its own success rate rates the two configurations exactly equally.

What this models and what it does not

The failure probabilities are declared and set by the slider; they are not measured from any real system, and the exact percentages belong to those settings. What does not depend on them: a duplicate application is invisible from inside the agent, an idempotency key changes the world and not the reply, and therefore no metric computed from replies can distinguish the two. Out of scope: partial failures inside a multi-step tool, ordering between concurrent calls, and servers that apply a write and then fail before recording the key — each of which makes exactly-once harder rather than easier.

How it works

// three outcomes, and only the middle one makes a retry dangerous
if (r < p.lost)                 return { applied: false, sawReply: false };  // never arrived
if (r < p.lost + p.replyLost)   return { applied: true,  sawReply: false };  // applied, reply lost
if (r < ... + p.refused)        return { applied: false, sawReply: true  };  // refused
                                return { applied: true,  sawReply: true  };  // fine

// an idempotency key does not stop the REQUEST, it stops the second APPLICATION
const wouldApply = a.applied && !(policy.idempotencyKey && served);
