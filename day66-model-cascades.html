AIFROMZERO · DAY 66

🪜 Model cascades — send everything to a cheap model first, escalate only what it is unsure about, and pay big-model prices on a fraction of your traffic. It works, and the whole thing turns on one quantity that has nothing to do with either model's accuracy: whether the small model knows when it is wrong. This page builds the real cost/accuracy frontier — every deferral threshold, plotted — and measures what actually moves it. The finding it is built around: at a fixed cheap-model accuracy, improving its calibration alone moves the frontier further than improving the expensive model. A perfectly calibrated 70% model beats a badly calibrated 80% one in a cascade, because the cascade never asks how often the small model is right — it asks how well its confidence ranks the cases it got wrong. Also implemented: why a fixed threshold silently changes your bill when traffic shifts, and why "escalate when the two models disagree" costs more than it saves. Pure vanilla JavaScript, one file, offline.

Calibration is the only dial here that is not about being right. It is whether the confidence score orders the errors — 0 means confidence is noise, 1 means every mistake is less confident than every correct answer.

The cascade never asks how often the small model is right

The idea is simple enough that it hides its own hard part. Run the cheap model. If it is confident, ship its answer. If not, escalate to the expensive one. You pay big-model prices on the escalated fraction only.

answer, confidence = small(x)
if confidence >= threshold: return answer         # cheap
return big(x)                                      # expensive

Every discussion of this focuses on the two accuracies. But look at what the code reads: it reads confidence. It never sees whether the small model was right. So the quantity that decides whether the cascade works is not accuracy at all — it is whether that confidence score ranks the errors below the correct answers.

Which is why calibration beats capability

At a fixed escalation budget, a perfectly calibrated 70% model beats a badly calibrated 80% one. The first knows exactly which 30% to hand over; the second escalates a random-ish selection and wastes most of the budget on cases it would have got right.

The ablation table on the page makes this concrete: hold escalation at 20% of traffic, then spend your improvement either on the small model's accuracy, its calibration, or the big model's accuracy. Calibration wins, and it is usually also the cheapest of the three to improve — temperature scaling on a validation set is a one-parameter fit.

A fixed threshold is not a fixed budget

You tune threshold = 0.85 on today's traffic and it escalates 18%. Then the traffic gets harder — a new customer segment, a seasonal shift, a prompt change upstream — and the same threshold now escalates 35%. Nothing in your code changed and your bill doubled.

The fix is to control the quantity you actually care about: pick the threshold as a quantile of recent confidence scores rather than a constant, so the escalation rate stays fixed and the accuracy moves instead. Which of the two you want to hold constant is a real decision, and the important part is making it deliberately rather than discovering it on an invoice.

Why "escalate on disagreement" is not a cascade

A router that runs both models and escalates when they disagree cannot save money: you have already paid for the expensive call in order to compare. It costs more than always using the big model, because you also paid for the small one.

It is a fine evaluation technique — disagreement is a good signal for finding hard cases offline. It is not a serving strategy, and the two get conflated constantly.

What a good confidence signal looks like

  • Sequence log-probability, length-normalised. Cheap, and better than nothing.
  • Self-consistency spread — sample k times, escalate when the answers disagree. Strong, and it costs k cheap calls.
  • A trained deferral head. Best, and it needs labelled examples of the small model failing — which you get for free from the escalated traffic itself.
  • Asking the model "are you sure?" — weak. Verbalised confidence is poorly calibrated and correlates more with the phrasing than with correctness.

The economics, honestly

The saving is bounded by the cost ratio. At a 25× ratio, escalating 20% of traffic costs roughly 20% × 25 + 80% × 1 = about 5.8 units against 25 for always-big — a 77% saving. At a 3× ratio the same cascade saves under half, and the added latency of a serial second call may not be worth it. The frontier on this page is drawn with the real numbers, so you can see where the strategy stops paying for itself.

And the honest caveat: a cascade adds a serial hop for escalated requests. Tail latency gets worse for exactly the hardest queries, which are often the ones a user is waiting on.

🔨 How it is built

1. Calibration as a dial, separate from accuracy

// correctness is drawn from accuracy; confidence is drawn so that its ORDERING
// tracks correctness by exactly `calibration`, and is noise at 0.
const correct = rnd() < accuracy;
const signal  = correct ? 1 : 0;
const conf    = calibration * signal + (1 - calibration) * rnd();

Two independent knobs. At calibration = 0 the confidence is pure noise and the cascade is choosing at random; at 1 every error sorts below every correct answer. The test asserts both endpoints, because a model where the two knobs were entangled could not show the finding at all.

2. The frontier, not a number

for (let t = 0; t <= 1; t += 0.01){
  const escalated = items.filter(i => i.conf < t);
  const acc  = mean(items.map(i => i.conf < t ? i.bigCorrect : i.smallCorrect));
  const cost = (1 - rate) * 1 + rate * ratio;
  frontier.push({ t, acc, cost, rate: escalated.length / items.length });
}

A cascade has no single score. It has a curve, and the only honest way to compare two configurations is at the same cost — which is why the ablation table pins the escalation rate at 20% rather than comparing free-floating accuracies.

3. Threshold by quantile, not by constant

const sorted = confidences.slice().sort((a, b) => a - b);
const threshold = sorted[Math.floor(rate * sorted.length)];   // fixed RATE

One line, and it converts "a threshold that drifts with traffic" into "a budget that does not". The drift table runs the same fixed constant against progressively harder traffic to show what it does otherwise.

4. What the tests pin

// the dials are independent
assert(accuracyOf(small) ≈ requested, at every calibration);
assert(aucOf(confidence) ≈ 0.5 when calibration = 0);
assert(aucOf(confidence) > 0.95 when calibration = 1);

// THE finding
assert(cascade(acc=0.70, cal=1.0) > cascade(acc=0.80, cal=0.2)) at the same budget;

// the frontier is a frontier
assert(monotone: more escalation never lowers accuracy);
assert(cost(rate=0) === 1 && cost(rate=1) === ratio);

// and the tempting router really is worse
assert(costOfDisagreementRouting > costOfAlwaysBig);

That last one is the assertion worth having. "Run both and compare" sounds thrifty, and one line of arithmetic shows it strictly dominates in the wrong direction — it is a technique that only survives because nobody prices it.
